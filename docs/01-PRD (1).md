# Product Requirements Document

## AutoApply Cloud

**Version:** 2.1
**Status:** Implementation baseline
**Date:** 2026-08-15

## 1. Product statement

AutoApply Cloud is a multi-user job-search workspace that turns a résumé and job
description into a truthful application plan and reviewed outreach draft. Users own
their account, résumé, profile, AI key, Gmail authorization, jobs, applications, and
history. The public web control plane runs on Vercel and durable state lives in
Supabase.

The product assists users; it does not impersonate them without review, collect third-
party passwords, promise unsupported platform access, bypass security checks, or send
unlimited unsolicited email.

## 2. Target users

- Job seekers who want one organized application pipeline.
- Candidates who bring a free/developer Groq API key for tailored writing.
- Candidates who optionally bring a Hunter API key to find a relevant recruiting
  contact for a company they selected.
- Users who want to send individually reviewed application/outreach emails from Gmail.
- Operators deploying a branded, tenant-isolated SaaS on Vercel and Supabase.

## 3. Core user journey

1. A visitor signs up or signs in through Supabase Auth.
2. **Profile:** the user completes their applicant profile, uploads and parses a PDF
   résumé, and saves a Groq API key in their encrypted account credential vault.
3. **Find jobs:** the user starts résumé-guided discovery. Groq derives bounded roles
   and keywords in the foreground; the worker uses those terms to filter Telegram/RSS
   candidates and runs a bounded LinkedIn guest search. LinkedIn is unofficial and
   best-effort, with no login, cookie, or Easy Apply.
4. **Form Pilot:** the user may paste a full numbered referral alert or one Google Form
   link. The parser extracts Company, Role, Batch, compensation, location, form links,
   application emails, and email subjects while ignoring known channel/premium-promotion
   links. Google Forms enter the preparation queue; email applications become available
   to **Mass Cold Email**. A queued form is not scanned until the user selects
   **Prepare form**. After that scan completes, the signed-in browser automatically
   requests one Groq suggestion set for the eligible form revision when a valid
   account Groq credential is configured. The backend resolves and decrypts that
   credential for the request without returning it to the browser. The user reviews
   and edits those exact answers,
   then chooses **Approve & submit in background** once. The API seals the latest exact
   revision, rejects incomplete required answers, and queues one idempotent submit. The
   worker reports success only after fresh Google Forms confirmation; otherwise it stops
   as `needs_attention` and may offer Live View. Google Forms never enter the cold-email
   review flow.
5. **Mass Cold Email:** this single sidebar destination contains **Build campaign** and
   **Review & send** subtabs. In **Build campaign**, the user adds and validates a
   Hunter key at the top of the view, selects at most 10 jobs, sees projected credit use
   inline, starts contact lookup, chooses one returned recruiting contact per job, and
   asks Groq for editable, fact-grounded email drafts. Both credentials remain in the
   account vault and are available across the user's signed-in devices; raw values are
   never returned. This destination contains email applications only, never Google
   Forms or ATS form-answer revisions.
6. In the second **Review & send** subtab, the user opens each email draft, edits it,
   and explicitly approves its exact message content. Approval is per email application,
   never inherited from the batch selection. Form-answer review remains in Form Pilot.
7. The user confirms the final send. The browser submits approved applications to the
   existing one-message Gmail endpoint sequentially, with the existing daily,
   duplicate-recipient, and idempotency gates applied to every message.
8. Applications, send outcomes, forms, and queued worker jobs remain visible in the
   dashboard.

## 4. Launch features

### 4.1 Identity and account lifecycle

- Email/password sign-up, sign-in, sign-out, email confirmation, and password reset via
  Supabase Auth.
- Account passwords remain in Supabase Auth's one-way password-hashing lifecycle;
  AutoApply never stores plaintext passwords or places password hashes in the reversible
  provider-credential vault.
- Cloudflare Turnstile tokens on sign-in, sign-up, and password-reset requests when the
  operator enables Supabase CAPTCHA protection.
- JWT-protected API requests; anonymous API access is limited to health/configuration.
- Account deletion workflow requiring a sign-in from the last ten minutes, documented
  data-access/export request boundary, private Storage cleanup, and provider cleanup.
  Bounded pseudonymous Gmail anti-abuse hashes are the documented exception.
- Every user-visible record is tenant-owned and protected by RLS.

### 4.2 Applicant profile and résumé

- Structured profile: name, email, phone, location, work authorization, experience,
  education, links, notice period, preferences, and free-form background notes.
- Private PDF upload directly to one of exactly five owned Storage slots,
  `<user-id>/resume-1.pdf` through `<user-id>/resume-5.pdf`, maximum 6 MB each.
- Server-side PDF text extraction and profile suggestions.
- Deterministic form mapping uses the reviewed `graduation_year` fact for recognized
  passout/graduation-year questions and a separately entered public HTTPS `resume_url`
  only for recognized résumé/CV link questions. The public URL is never inferred from,
  or replaced by, the private uploaded PDF path or an expiring signed URL.
- Transactional registration verifies the Storage object and atomically makes the
  selected résumé active while deactivating the previous active résumé.
- Deleting a résumé removes its private object and résumé metadata; existing jobs,
  applications, drafts, and send history remain intact.
- No local root-level `profile.json` or shared `cv.pdf` in hosted mode.

### 4.3 Bring-your-own Groq and Hunter

- Key entry, validation, masked display, replacement, and deletion.
- Groq and Hunter keys are account-scoped and stored with authenticated encryption in
  the service-role-only `user_provider_credentials` table. Browser roles cannot read
  the table. Ordinary sign-out leaves the account credential available for the user's
  next sign-in and other signed-in devices; explicit removal or account deletion deletes
  the credential row.
- The first-party browser submits a raw key only over authenticated HTTPS when saving or
  replacing it. Save/list responses expose only configured state, verification metadata,
  timestamps, and a bounded masked hint—never plaintext or ciphertext.
- For each authorized request, the API resolves the credential by verified account ID
  and decrypts it only inside the trusted backend for the operation. A worker resolves
  and decrypts only the credential bound to its claimed job (currently the tenant
  Browserbase credential for managed-browser work). Raw credentials never enter queue
  payloads, progress/results, URLs, analytics, error messages, or application logs.
- API keys require reversible authenticated encryption because the backend must recover
  them for provider calls. This is intentionally different from Supabase Auth password
  hashing, which is one-way and is not used for API keys.
- `TOKEN_ENCRYPTION_KEY` must be backed up and remain byte-for-byte identical in the API
  and persistent worker environments. An unplanned change or loss makes existing vault
  ciphertext unreadable.
- Legacy user-scoped Groq/Hunter keys in browser `localStorage` are migrated once on the
  next authenticated credential load. The client removes the old copy only after the
  server confirms the vault import or an existing account credential; a failed import is
  surfaced and retains the legacy value for a safe retry. New keys are never persisted
  in browser storage.
- Default production model: `openai/gpt-oss-120b`, configurable by the operator.
- Résumé-guided discovery uses the saved Groq credential in
  `POST /api/v1/discovery/resume-guided`; the foreground response returns the bounded
  search plan and two durable discovery jobs, never the key.
- After a user explicitly scans a Google Form, the signed-in browser triggers the
  foreground form-suggestion endpoint once for each eligible revision. The API resolves
  the saved Groq credential; the request remains a reviewable suggestion—not approval—and
  is deduplicated in browser state without storing the credential there.
- Optional Hunter key entry, validation, masked display, replacement, and deletion use
  the same account vault. Authenticated, user-initiated Hunter endpoints resolve it in
  the backend, never put it in a URL, and never return it.
- `POST /api/v1/hunter/validate` returns a small validity/quota summary.
  `POST /api/v1/jobs/{id}/contacts/hunter` searches at most 10 HR contacts for an owned
  job's company and returns allowlisted contact fields for the user to choose from.
- There is no operator `HUNTER_API_KEY` and no unattended Hunter contact-harvesting job.
  Credential availability never substitutes for the user's explicit lookup, generation,
  review, approval, or send actions.

### 4.4 Job and application workspace

- Create jobs from title/company/JD/URL/location/contact fields.
- List, filter, edit, archive, and deduplicate jobs by user and normalized URL.
- Start résumé-guided discovery from a parsed active résumé. Favor saved target roles,
  combine bounded Groq-derived and saved skills, choose a user/saved/profile location,
  and return the search plan for inspection.
- Queue a bounded LinkedIn guest search plus Telegram/RSS discovery. Apply the
  résumé-derived terms to Telegram/RSS records before persistence; retain LinkedIn's
  explicit unofficial/best-effort label and guest-only boundary.
- Show a tenant-scoped, normalized-URL-deduplicated Google Forms queue containing
  direct saved forms and form URLs discovered in saved-job metadata. The queue offers
  save and explicit scan actions. Once an explicit scan finishes, Form Pilot applies
  exact Profile facts and the signed-in browser may automatically trigger Groq
  suggestions using the account credential for unresolved questions. It exposes no
  second AI-fill action and never
  approves or submits without the user's explicit combined approval action.
- Make referral-message parsing Form Pilot Stage 01. Accept a complete Telegram,
  WhatsApp, or email digest; split numbered Company/Role postings; retain labeled Batch,
  CTC/Stipend, and Location facts; route Google Forms to Form Pilot and application
  email addresses to jobs available in Mass Cold Email; and filter recognized
  channel/premium-promotion links. Show routing counts without automatically preparing,
  approving, submitting, drafting, or sending anything.
- Generate a tailored outreach/application draft from the user's own facts.
- Keep Google Form schema, answer suggestions, exact-answer editing, approval-bound
  submit progress, verified confirmation, and needs-attention fallback inside Form
  Pilot. Do not place Google Form revisions in the Mass Cold Email draft list.
- Let the user select at most 10 non-archived saved jobs for one UI outreach batch,
  see projected Hunter credit use inline, explicitly start the lookup, select a contact
  for each job, and generate drafts with Groq. Contact candidates and batch selection
  are non-authoritative browser state.
- Edit, approve, cancel, and track application status.
- Maintain a user-specific answer bank for reusable screening answers.

### 4.5 Gmail connection and sending

- “Connect Gmail” starts Google's web OAuth flow with the platform-managed client by
  default when it is available.
- An advanced authenticated user may save a Google **Web application** OAuth client ID
  and secret, explicitly select it for the flow, and later remove it. A Google Cloud
  API key is not accepted as OAuth client credentials.
- Request only identity plus `gmail.send` for launch.
- Use one operator-configured callback for both credential sources. Do not accept a
  per-user redirect URI, scope list, authorization endpoint, or token endpoint.
- Store refresh/access tokens and user-managed client credentials encrypted in separate
  server-only tables with no browser read policy. Never return a saved client secret or
  persist it in browser storage.
- Show connected address, connection health, scope, and disconnect action.
- Serialize OAuth start/callback/reconnect/disconnect by a per-user generation so a
  stale callback cannot recreate a superseded or disconnected Gmail connection.
- Bind each OAuth state and connected account to its selected credential source and,
  for a user-managed client, its exact credential generation. Require Gmail disconnect
  before that client can be replaced or deleted.
- On disconnect, remove local token rows and attempt Google revocation. If Google does
  not confirm revocation, tell the user to remove access in Google Account settings.
- Explain that an External Google app in Testing must list test users and, because the
  product requests `gmail.send`, its test-user grants and refresh tokens expire seven
  days after consent. Explain that public production use requires the project owner to
  publish the app and complete brand/domain and sensitive-scope verification.
- Send only a user-selected, approved message; attach the user's private résumé.
- The outreach UI may send at most 10 individually approved applications in a batch,
  only after a final confirmation, by invoking the existing single-send API
  sequentially. Each call independently reserves and enforces daily caps, duplicate
  recipient protection, idempotency, and provider-account limits.
- Enforce per-user daily caps, idempotency, duplicate-recipient protection, and audit
  events. No autonomous bulk blast endpoint.
- Retain only domain-separated provider-account and recipient SHA-256 hashes, without a
  user ID or plaintext address, for provider-level cap/duplicate enforcement. These
  rows expire no later than 90 days and can briefly outlive account deletion. Expired
  rows no longer affect controls; hourly and reservation-path cleanup physically remove
  them. Cron failures can delay physical deletion and must be monitored.

### 4.6 Provider connection center

- A catalog explains each provider's actual integration mode:
  `oauth`, `public_ats`, `managed_browser`, `manual_only`, or `partner_required`.
- LinkedIn supports only profile URL/manual handoff at launch; LinkedIn OIDC is not a
  launch connection and would not authorize candidate application automation.
- LinkedIn candidate auto-apply is visibly unavailable without approved partner access.
- Permitted remote-browser providers use isolated contexts and a Live View for user
  login/MFA. Context deletion is available.
- Greenhouse is the initial aligned generic application handler. One-page Google Forms
  use a stricter launch flow: durable scan, browser-triggered Groq suggestions, exact
  Form Pilot review, explicit approval-bound background submit, and verified provider
  confirmation. Live View is retained only for `needs_attention`; it is not a required
  success step. Lever and Ashby passed read-only scan canaries but remain disabled
  pending controlled submit-confirmation tests; Wellfound remains disabled pending a
  signed-in canary. YC's finished exact-job flow accepts only a user-saved current public
  YC job-detail URL, reuses the tenant's isolated persistent Browserbase BYOK context for
  sign-in, scans visible fields with Playwright in the separate worker, grounds reviewable
  answers in the owned résumé/profile with Groq, seals one approved submit, and reports
  success only after fresh provider confirmation. It remains operator-allowlist gated
  until the signed-in canary passes. Optional query, remote, and limit preferences never
  scrape/discover YC or enqueue a YC provider request. The generic exact-host
  company-form adapter remains an internal controlled canary. Cutshort and
  Instahyre are connection-only until tenant-aware multi-step application handlers are
  implemented; multi-page or branching Google Forms are unsupported.
- Permitted ATS work is submitted as durable jobs. Playwright controls Browserbase only
  in the continuously running worker outside Vercel; Vercel never launches Chromium or
  runs the worker.

### 4.7 Durable work and observability

- Any long-running operation creates an `automation_jobs` record and returns HTTP 202.
- `POST /api/v1/discovery/resume-guided` performs the request-bounded Groq planning step,
  then creates one LinkedIn guest job and one Telegram/RSS job with derived idempotency
  keys. Hunter lookup and draft generation remain explicit foreground operations because
  they require user initiation and review; account-level credential availability does
  not change that control boundary.
- A worker atomically claims one job, reports progress, and persists a terminal result.
- The worker must run continuously on a persistent process host outside Vercel; a
  request-bounded Vercel Function is not a worker deployment.
- Users can inspect pending/running/succeeded/failed/needs-attention status.
- Jobs are idempotent and carry no raw OAuth tokens, Groq keys, cookies, or résumé bytes.

## 5. Explicit launch exclusions

- Collecting Gmail, LinkedIn, or job-board passwords.
- Uploading arbitrary desktop OAuth token files.
- Treating a Google Cloud API key as Gmail OAuth authorization.
- LinkedIn scraping or Easy Apply automation in the public hosted product.
- CAPTCHA solving, security-check bypass, proxy rotation to evade controls, or account
  restriction evasion.
- Unreviewed bulk cold email.
- Autonomous contact harvesting, draft approval, or multi-recipient send. The bounded
  outreach selection is UI orchestration around explicit Hunter, Groq, approval, and
  single-message Gmail operations.
- Gmail inbox/reply access until restricted-scope approval is separately completed.
- Treating Vercel local disk or process memory as durable state.

## 6. Product principles

- **Accurate capability labels:** OAuth identity is never presented as application API
  access.
- **User control:** generation, approval, send, disconnect, and deletion are explicit.
- **Bounded orchestration:** selecting several jobs never authorizes contact lookup,
  approves content, or sends email; each checkpoint remains separately visible.
- **Truthful applications:** generated content may use only the supplied profile,
  résumé, and JD; unknown facts remain unknown.
- **Tenant isolation:** authorization is derived from the verified JWT, never a request
  body `user_id`.
- **Durability:** every externally meaningful action has a database state and
  idempotency key.
- **Deployability:** the web product is stateless and Python 3.12 compatible.

## 7. Success criteria

- A fresh user completes onboarding without operator intervention.
- Cross-tenant reads/writes fail at both API and RLS layers.
- A 5 MB PDF uploads directly to Storage and can be parsed without passing through the
  Vercel request body.
- A sixth résumé object, a non-slot filename, and a cross-user slot are rejected; two
  concurrent registrations cannot create two active résumés.
- Graduation/passout questions resolve deterministically from the reviewed profile year,
  and résumé-link questions remain blank until the user supplies a public HTTPS résumé
  URL distinct from the private uploaded PDF.
- Groq and Hunter credentials survive refresh/sign-out and are available on another
  signed-in device, while replacement, explicit deletion, and account deletion update or
  remove only that tenant's encrypted vault rows. No credential API response contains a
  raw key or ciphertext.
- Résumé-guided discovery returns bounded, inspectable roles/keywords, queues exactly
  the LinkedIn guest and Telegram/RSS runs for the tenant, and filters public-feed
  results using those terms without putting the Groq key into a queue payload.
- The Google Forms queue is tenant-scoped, deduplicated by normalized URL, links the
  latest application when one exists, and requires an explicit scan action. When that
  scan succeeds and a Groq key exists, Form Pilot automatically requests one suggestion
  set for the eligible revision; the user can edit and must explicitly choose the exact
  approval-bound submit action. The queued job is bound to the latest immutable revision
  and complete required-answer preflight. Only fresh provider confirmation may produce
  `application_submitted`/`confirmed`; uncertainty becomes `needs_attention`, with Live
  View only as a fallback. No Google Form appears in Mass Cold Email.
- A Hunter operation resolves the account credential in the trusted backend, never puts
  a raw key in logs, URLs, or queue payloads, and returns at most the requested 1–10 HR
  contacts for an owned job.
- API and worker processes using the same `TOKEN_ENCRYPTION_KEY` can resolve only the
  tenant/job-scoped credential they need; a mismatched key fails closed without exposing
  secret material.
- A selected 10-job outreach set cannot send until every included message has been
  individually reviewed and approved and the user confirms the final action. Sends are
  sequential and a cap, duplicate, idempotency, or provider gate still stops/fails the
  affected request safely.
- A Gmail OAuth callback connects the initiating user and an approved message sends at
  most once.
- The default platform OAuth client and the advanced user-managed Web client each
  complete a connection using the same exact callback; status responses never expose a
  user-managed secret.
- Replacing or deleting a user-managed client while Gmail is connected fails and
  succeeds only after disconnect; a callback bound to an older credential generation
  cannot save tokens.
- A stale OAuth callback cannot reconnect after disconnect; revocation failure is
  visible without retaining local token material.
- A session whose last verified sign-in is older than ten minutes cannot permanently
  delete an account; the normal protected sign-in flow restores eligibility.
- A duplicate queue delivery does not repeat an application or email send.
- Unsupported providers explain the limitation instead of starting broken automation.
- The Vercel deployment starts without SQLite, APScheduler, local Chrome, or root-level
  user files.

## 8. Rollout

### Phase A — private preview

Supabase auth/RLS, profile, résumé, BYO Groq/Hunter, résumé-guided discovery, manual
jobs, Google Forms scan/automatic-suggestion/exact-review/background-submit/verified-
confirmation flow,
bounded email outreach drafting, Gmail test users through
the platform client and advanced user-managed clients, sequential individually reviewed
sends, and application tracking. Testing users are told to expect Google
reauthorization after the seven-day testing grant expires.

### Phase B — verified public beta

Google sensitive-scope verification for the platform-managed client, custom domain,
privacy/terms pages, abuse controls, custom SMTP for Supabase Auth, monitoring, account
deletion, and production quotas. Users publishing their own OAuth project remain
responsible for its Google verification and policies.

Promotion to this phase is blocked until the operator has deployed and exercised the
real migration in a separate staging project (including RLS, Storage, OAuth-generation,
send-reservation, account-deletion, and queue concurrency tests), verified Vercel and
Supabase production configuration, completed Google verification for the platform
client's exact domain and scopes, verified the advanced path's Testing/verification
disclosures, and replaced every operator identity/contact/governing-law placeholder in
the legal pages. The repository does not supply or infer those operator-specific facts.

### Phase C — permitted automation connectors

Deploy the worker, enable only reviewed provider connectors, add managed-browser login
for permitted sites, and pursue official platform partnerships where required.
